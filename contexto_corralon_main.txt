REGLAS DE TRABAJO
=================

- Trabajar en modo rápido por defecto: ubicar el código puntual, modificarlo y
  volver con el resultado.
- No abrir, inspeccionar ni depurar el navegador salvo pedido explicito.
- No asumir decisiones, comportamientos o alcances que el usuario no haya pedido.
- Si aparece cualquier duda, ambigüedad o decisión con más de una interpretación,
  preguntar al usuario antes de modificar.
- Solo hacer una revisión profunda cuando el usuario lo pida específicamente.
- No crear copias locales .bak ni backups de ejecutables, bases Access o archivos
  antes de reemplazarlos. El usuario ya tiene sus propios backups.
- Cuando el usuario pide diagnosticar o revisar sin tocar nada, las consultas a
  Access, Supabase y archivos deben ser de solo lectura.
- En Caja, la copia local nunca debe publicarse automaticamente sobre Firebase.
  Cargar, navegar, recuperar cache o perder el foco no autoriza subir una tabla.
  Las modificaciones del usuario deben comprobar el estado remoto antes de guardar.


1. DESCRIPCION GENERAL
======================

Corralonprogreso-main es un sistema web para administrar y consultar distintas
áreas del corralón:

- catálogo público y carrito;
- presupuestos;
- remitos e historial;
- pedidos a proveedores;
- artículos faltantes;
- proveedores y listas de precios;
- carga de stock;
- actualización de artículos;
- control diario de caja;
- comprobantes;
- garantías;
- usuarios, sesiones y permisos;
- calculadoras;
- administración del catálogo público.

No está construido como una aplicación con un framework único. La mayor parte
del sistema está formada por páginas HTML independientes. Cada página contiene
su estructura, estilos y bastante lógica JavaScript dentro del propio archivo.

También existen módulos JavaScript compartidos que concentran funciones usadas
por varias páginas.

Muchas páginas son archivos grandes y monolíticos. Antes de modificar una
función conviene confirmar si:

1. está definida dentro de la página;
2. proviene de funciones.js;
3. proviene de corralon-system.js;
4. depende de menu-auth-guard.js;
5. utiliza Firebase, Supabase, Cloudinary o almacenamiento local.


2. ARCHIVOS PRINCIPALES
=======================

index.html
----------

Es la lista de precios y catálogo público.

Incluye, entre otras cosas:

- carga y visualización del catálogo;
- búsqueda por código o descripción;
- tarjetas de productos;
- detalle ampliado del artículo;
- stock por sucursal;
- precios, ofertas y descuentos;
- carrito;
- compartir artículos;
- presupuestos;
- cálculo especial para cerámicos;
- acceso a funciones administrativas cuando existe una sesión válida.

La fuente principal vigente del catálogo es la tabla catalogo_articulos de
Supabase. index.html carga esa tabla mediante corralon-system.js. Los JSON viejos
de Cloudinary se conservan solamente como respaldo/fallback y no deben borrarse
sin pedido explícito.

Campos importantes que llegan desde la exportación de artículos:

- IDArt o código interno;
- CodProv o código de proveedor;
- descripción;
- stock por sucursal;
- PrecioCpraCI: precio de costo con impuestos;
- PrecioVta3: precio de venta al público;
- PorcGanMin: porcentaje/margen exportado desde Access;
- datos de rubro, imágenes, ofertas y metadatos.

El sistema de descuentos del catálogo utiliza el costo con impuestos y el precio
de venta para calcular el margen real. El descuento:

- no se aplica a artículos que ya están en oferta;
- tiene un máximo del 25%;
- no debe dejar un margen final inferior al 3%;
- se refleja en el detalle del producto;
- se mantiene al agregar el artículo al carrito;
- también se usa en el presupuesto de cerámicos;
- se identifica con chips verdes de “Oferta” o “Descuento”.

En el detalle ampliado, el código de proveedor se muestra junto a IDArt solamente
cuando existe una sesión interna iniciada desde menu.html. Para el público no
autenticado permanece oculto.


menu.html
---------

Es el menú interno principal y también administra el inicio de sesión interno.

Funciones principales:

- inicio y cierre de sesión;

- accesos a las distintas páginas;
- notificaciones;
- pendientes rápidos;
- cotización del dólar oficial;
- usuario activo;
- objetivos y otros datos internos.

La cotización del dólar se muestra para todos los usuarios y comparte el origen
utilizado por caja.html.

El alta rápida de pendientes permite guardar con Enter, limpiar y recuperar el
foco inmediatamente, mientras la publicación se completa en segundo plano.


usuarios.html

Administra los usuarios internos del menú:

La colección principal de usuarios internos en Firebase se llama:

menuUsuarios


soloadmin.html
--------------

Panel de administración del catálogo público.

Maneja datos como:

- imágenes;
- ofertas;
- etiquetas;
- información publicada;
- ajustes visuales o comerciales del catálogo;
- metadatos adicionales de artículos.

El importador masivo de este panel realiza una sincronización completa:

- en localhost usa el mismo recorrido externo que dispara Access;
- fuera de localhost usa la Edge Function catalogo-sync-remoto;
- consolida las filas repetidas por código usando IdSuc 1 para Progreso e IdSuc
  2 para Calle 5;
- conserva imágenes, detalle, tags, etiquetas, ofertas y demás metadatos
  mantenidos manualmente;
- los artículos que ya no están en la importación completa quedan inactivos.

Al imprimir un remito también debe generarse o conservarse la notificación
correspondiente. El contenido copiable del remito utiliza IDArt y cantidad.

Historial de presupuestos y remitos.

Permite:

- abrir registros anteriores;

- editar remitos;

El editor de ítems tiene navegación tipo Access:

- no se debe guardar una fila vacía como un artículo con cantidad cero;
- el botón morado “+” confirma/agrega el nuevo registro.

---------------------

Contiene funciones compartidas para presupuestos y documentos:

- armado de datos;

- utilidades reutilizadas por index.html e historial/remitos.


pedidos.html
------------

Administra pedidos a proveedores.

Flujo general:

1. se selecciona un proveedor;
2. se selecciona una sucursal;
3. se buscan faltantes pendientes para esa combinación;
4. los artículos se importan al pedido;
5. el pedido puede quedar en edición o revisión;
6. puede generarse PDF o Excel;
7. al confirmarse se actualizan los faltantes asociados.

Relación importante con faltantes:

- un faltante importado se marca como pedido;
- si se elimina del pedido antes de confirmarlo, debe desmarcarse;
- si se elimina el pedido completo, se deben desmarcar sus artículos;
- al generar el pedido definitivo, los faltantes correspondientes se eliminan
  o se resuelven según el flujo vigente.

Los botones sensibles, como eliminar pedido y determinadas exportaciones, están
limitados según el rol del usuario, especialmente al administrador.


faltantes.html
--------------

Tabla de artículos faltantes.

Permite:

- cargar faltantes;

- asignar sucursal;
- filtrar por código de proveedor;
- filtrar por artículo;
- filtrar por proveedor;
- filtrar por sucursal;
- marcar y sincronizar el estado de pedido.

Las sucursales normales son:

- Suc. Progreso y Ruta;
- Suc. Calle 5 y Espana.

La lógica central de faltantes está compartida parcialmente desde
corralon-system.js.

Incluye:

Los códigos pueden contener caracteres invisibles, saltos de línea o espacios

sin alterar el código visible que necesita el usuario.


cargastock.html
---------------

Herramienta tipo planilla para preparar cargas de stock y costos.

Funciones principales:

- selección de proveedor;
- carga del JSON específico del proveedor;
- carga del índice principal de artículos;
- pegado de filas desde Excel o Access;
- edición por celdas;
- validación de códigos;
- validación del proveedor;
- cálculo de descuentos;
- precio final;
- precio final por cantidad;
- comparación contra datos del sistema;
- copiado de las filas válidas;
- menús contextuales;
- unificación temporal de filas;
- inserción y eliminación temporal de filas;
- recálculo;
- búsqueda en listas;
- apertura de la web del proveedor.

Reglas importantes de validación:

- la coincidencia del código se comprueba estrictamente contra el índice
  principal de index.html;
- el código debe coincidir de forma exacta después de normalizar caracteres
  invisibles;
- también debe coincidir el proveedor correspondiente;
- no se debe usar la lista JSON individual del proveedor para decidir si la fila
  es válida en el índice;
- las filas sin coincidencia correcta se muestran en rojo;
- las filas válidas se muestran en verde;
- si un código tiene más de una coincidencia en el índice, la copia continúa,
  pero aparece una advertencia con el código y las descripciones encontradas.

El índice completo no debe guardarse entero en localStorage porque puede superar
la cuota del navegador. La carga debe funcionar en memoria y la caché local debe
ser reducida o prescindible.

El popup “Comparar” presenta dos lados:

- Cargar Stock;
- Sistema.

La comparación principal se realiza por código. Las descripciones pueden ser
diferentes y no deben invalidar una coincidencia de código. Los precios admiten
una tolerancia del 2%.

Las modificaciones realizadas dentro del comparador son temporales y no deben
alterar la tabla original salvo que exista una acción explícita para hacerlo.

Los campos de cabecera Desc. factura, Desc. final factura, Flete, IVA incluido e
IVA funcionan como ajustes temporales de la planilla. Al modificarlos se recalcula
la carga actual, pero no se actualiza el registro persistente del proveedor en
Supabase. Los valores originales vuelven al recargar la página o seleccionar
nuevamente el proveedor. La edición persistente se realiza desde proveedores.html.

caja.html
---------

Control diario de caja.

Permite consultar y trabajar por:

- Suc. Progreso y Ruta;
- Suc. Calle 5 y Espana;
- Todas las sucursales.

Muestra, entre otros:

- movimientos del día;
- caja inicial;
- ingresos/egresos;
- importe final;
- transferencias de Mercado Pago;
- transferencias del sistema;
- medios de pago;
- diferencias;
- cotización del dólar;
- información guardada por fecha.

Los movimientos sin sucursal asignada son globales y solo se muestran cuando se
elige “Todas las sucursales”.

La opción “Separar” permite incluir o excluir determinados medios de pago por
sucursal. La selección se conserva localmente, pero no debe excluir movimientos
globales.

La fuente remota debe prevalecer sobre una copia local. Una caché local nunca
debe sobrescribir Firebase o Supabase con datos vacíos o antiguos.

Las exportaciones de Access generan JSON temporales de entrada. caja.html no
debe depender directamente de esos JSON: el contenido se copia a tablas de
Supabase y desde allí se consulta por fecha. Las modificaciones manuales de la
tabla (unificar, separar, eliminar una fila o agregarla) son persistentes. El
botón general "Eliminar registro" limpia el estado persistente del día para que
la siguiente actualización de Access pueda volver a importar todo desde cero.

El total de una fila se calcula como:

Caja inicial + Movs. Día + Imp. I/E = Imp. Final

4. SERVICIOS Y ALMACENAMIENTO
=============================

El proyecto utiliza una combinación de servicios. No existe una única base de
datos para todo.


Firebase / Firestore
--------------------

Se utiliza principalmente para:

- usuarios internos;
- sesiones y permisos;
- configuración y metadatos auxiliares;
- notificaciones;
- pedidos;
- faltantes sincronizados;
- algunos estados compartidos.

Algunas páginas usan Firebase modular y otras usan las librerías compat.


Supabase
--------

Se utiliza para:

- proveedores;
- listas de precios;
- catálogo principal en catalogo_articulos;
- metadatos manuales del catálogo;
- manifiestos de JSON por proveedor;
- estados persistentes;
- historial diario de caja y transferencias;
- saldos y facturas de proveedores;
- historial y datos complementarios;
- almacenamiento de archivos en algunos módulos.

La configuración principal está centralizada parcialmente en
corralon-system.js, aunque algunas páginas también contienen llamadas propias.


Cloudinary
----------

Se utiliza como almacenamiento de archivos JSON grandes y otros recursos.

Ejemplos:

- catálogo principal;
- listas JSON de proveedores;
- exportaciones de caja;
- archivos auxiliares de publicación.

Firebase o Supabase pueden guardar el enlace al archivo vigente, mientras que el
contenido grande se aloja en Cloudinary.


localStorage, sessionStorage e IndexedDB
----------------------------------------

Se utilizan para:

- cachés;
- sesión;
- borradores;
- preferencias;
- selecciones;
- datos temporales;
- acelerar la apertura de páginas;
- conservar estados de interfaz.

Regla de datos importante:

Una copia local es auxiliar. No debe reemplazar silenciosamente información
remota válida con datos viejos, incompletos o vacíos.


5. FLUJO DEL CATALOGO PRINCIPAL
===============================

El catálogo público se genera actualmente con este recorrido:

Access
  -> exportación de C:\Update\Articulosexp.xls
  -> C:\Update\run_sync_articulos_silent.vbs
  -> scripts de C:\Update\actualizaciones\Subir Lista Index
  -> parseo a JSON temporal
  -> sincronización completa de catalogo_articulos en Supabase
  -> carga directa desde Supabase mediante corralon-system.js

El importador masivo de soloadmin.html debe producir el mismo resultado. En
localhost llama a /api/catalog-sync/import y ejecuta catalog-sync-import.bat con
--full. En corralonprogreso.com utiliza catalogo-sync-remoto por lotes y luego
finaliza la versión completa.

Código VBA conocido del botón de exportación:

- exporta la consulta/tabla ExportArts;
- genera C:\Update\Articulosexp.xls;
- ejecuta C:\Update\run_sync_articulos_silent.vbs;
- el proceso continúa mediante scripts externos.

Archivos externos relacionados:

- Articulosexp.xls;
- run_sync_articulos_silent.vbs;
- run_sync_articulos.bat;
- C:\Update\actualizaciones\Subir Lista Index\parse_excel_to_json.js;
- C:\Update\actualizaciones\Subir Lista Index\sync_catalogo_supabase.js;
- catalog-sync-import.bat dentro del proyecto web.

Los scripts de parseo/sincronización deben conservar:

- PrecioCpraCI;
- PrecioVta3;
- PorcGanMin;
- imágenes;
- ofertas;
- metadatos ya publicados.

El MDB de Access no forma parte del repositorio web.


6. FLUJO DE PROVEEDORES Y CARGA DE STOCK
========================================

Flujo aproximado:

proveedores.html
  -> datos de proveedor en Supabase
  -> actualizar articulos.html
  -> lista_precios / lista_precios_meta
  -> JSON específico del proveedor
  -> cargastock.html / listasproveedores.html / faltantes.html

El catálogo principal y la lista específica de un proveedor cumplen funciones
distintas:

- índice principal: confirma si existe la combinación exacta de código y proveedor;
- JSON del proveedor: ayuda a buscar descripciones, precios y artículos del
  proveedor seleccionado.

No deben intercambiarse estas responsabilidades.


7. FLUJO FALTANTES Y PEDIDOS
============================

Flujo aproximado:

faltantes.html
  -> artículo pendiente con proveedor y sucursal
  -> selección del proveedor en pedidos.html
  -> selección de sucursal
  -> importación automática
  -> artículo marcado como pedido
  -> revisión
  -> PDF o Excel
  -> confirmación y limpieza del faltante

Si el artículo sale del pedido antes de completarse, el vínculo con faltantes
debe revertirse.


8. FLUJO DE REMITOS, PRESUPUESTOS Y NOTIFICACIONES
==================================================

index.html
  -> presupuesto web
  -> historial.html
  -> notificación en menu.html

remitos.html
  -> remito
  -> PDF/impresión
  -> historial.html
  -> notificación en menu.html

Las notificaciones deben incluir el número y, cuando corresponda, el cliente.
Imprimir no debe impedir que quede registrada la notificación.


9. FLUJO DE CAJA
================

Access genera informes diarios que luego se transforman en JSON temporales de
importación para caja.html.

Flujo aproximado:

Access / informe diario
  -> archivo de exportación
  -> JSON temporal de caja

Optimizacion del consumo de Supabase
------------------------------------

Problema diagnosticado:

- La organizacion supero ampliamente el cupo de transferencia del plan gratuito.
- El consumo principal aparecia como PostgREST Egress, no como Storage Egress.
- Los dos responsables mas importantes eran index.html y listasproveedores.html.
- index.html descargaba repetidamente el catalogo completo de articulos aunque
  la mayoria de las filas no hubiera cambiado.
- listasproveedores.html consultaba periodicamente los datos remotos con una
  frecuencia aproximada de 10 segundos.
- pedidos.html y faltantes.html dependian de la actualizacion de JSON realizada
  por listasproveedores.html, por lo que abrir una pantalla podia provocar
  lecturas completas o dejar otra pantalla con informacion desactualizada.

Solucion implementada para el catalogo de index:

- Se incorporo una version global del catalogo y una version por articulo.
- El navegador conserva el catalogo en IndexedDB junto con la ultima version
  aplicada.
- Al abrir index.html se consulta primero el unico registro de version global.
- Si la version remota coincide con la version local, se utiliza IndexedDB y no
  se descarga nuevamente la tabla completa.
- Si existe una version nueva, solo se solicitan los articulos cuya version sea
  posterior a la que posee IndexedDB y se actualizan esas filas localmente.
- Si el navegador quedo varias versiones atras, descarga todos los articulos
  modificados entre su version y la version actual.
- Las altas, modificaciones y bajas logicas de articulos incrementan la version
  correspondiente y tambien actualizan la version global.
- La edicion individual desde Corralon System incrementa la version del articulo.
- El exportador de Access ubicado en
  C:\Update\actualizaciones\Subir Lista Index compara la exportacion nueva con
  el estado publicado y solo incrementa la version de las filas modificadas.
- El importador masivo de soloadmin.html sigue siendo una sincronizacion completa:
  fuerza una version nueva para todos los articulos importados y actualiza la
  version global para que todos los clientes reemplacen su cache.
- La informacion manual de catalogo_articulos_edicion, como imagenes, etiquetas,
  tags, ofertas y detalles, permanece separada y no debe sobrescribirse durante
  una actualizacion del catalogo base.

Solucion implementada para listas y pantallas internas:

- El sondeo automatico de listasproveedores.html paso de aproximadamente 10 a
  60 segundos.
- index.html, listasproveedores.html, pedidos.html y faltantes.html actualizan al
  abrir o recargar la pagina y evitan consultas completas continuas.
- pedidos.html y faltantes.html ahora consultan la version del JSON igual que
  listasproveedores.html.
- Cada pantalla puede detectar por si misma si el JSON cambio; ya no depende de
  que listasproveedores.html haya sido abierta previamente para actualizarlo.
- Cuando la version no cambio se reutiliza la copia local. El contenido remoto
  se descarga solamente cuando la version publicada es diferente.

Resultado esperado:

- La transferencia diaria de PostgREST debe disminuir de forma marcada despues
  de que los archivos optimizados esten publicados y los clientes los recarguen.
- El consumo ya acumulado dentro del periodo de facturacion no se reinicia por
  aplicar el parche; Supabase lo mantiene hasta el comienzo del siguiente ciclo.
- Para verificar la mejora se debe observar Egress per day durante las horas o
  dias posteriores a la publicacion, no solamente el total acumulado del periodo.
- Si el consumo vuelve a crecer, revisar primero solicitudes repetidas a
  catalogo_articulos, manifiestos/versiones y listas de proveedores antes de
  cambiar RLS o Storage.

Sincronizacion incremental y consumo
------------------------------------

- La prioridad general es conservar una copia local util en IndexedDB y consultar
  remotamente versiones, cursores o filas nuevas, no descargar colecciones
  completas cada vez que se abre una pantalla.
- catalogo_articulos utiliza version global y version por articulo. Una version
  igual reutiliza IndexedDB; una superior descarga solamente los cambios.
- Una sincronizacion completa sigue siendo valida como recuperacion, importacion
  masiva o reconstruccion de cache, pero no debe convertirse en el recorrido
  habitual de cada apertura.
- faltantes.html guarda inmediatamente el estado local, mantiene pendingSync y
  envia en segundo plano solamente las filas modificadas. Las filas remotas se
  comparan mediante syncId; una eliminacion se representa como cambio remoto y no
  obliga a reescribir toda la tabla.
- pedidos.html arma el pedido localmente y publica el pedido completo cuando se
  envia a revision. Para recibir cambios usa Firestore Realtime, consulta solo
  documentos con syncId mayor al cursor guardado en IndexedDB y combina esos
  cambios con la cache local.
- Firestore tiene limites diarios de lecturas y escrituras. No agregar listeners
  por fila, guardados en cada pulsacion ni reescrituras de colecciones completas.
- Los errores resource-exhausted indican cuota de Firestore agotada. Los errores
  ERR_BLOCKED_BY_CLIENT suelen provenir de bloqueadores/extensiones y deben
  distinguirse de una cuota agotada.
- El egress de Supabase debe vigilarse por tipo. PostgREST Egress alto suele
  significar consultas REST que devuelven muchas filas; no es lo mismo que
  Storage Egress ni Realtime Egress.
- Forzar repetidamente la actualizacion completa del catalogo desde Administrar
  pagina puede producir picos grandes de PostgREST Egress aunque el flujo
  incremental normal este funcionando.
